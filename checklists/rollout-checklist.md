# AIN-Loop 90 天落地清单

## 0. 启动前：选择试点（第 0–2 周）

- [ ] 选择 1 个 R0/R1 服务：活跃开发、有稳定 CI、拥有明确服务和代码所有者。
- [ ] 基线化近 90 天数据：Lead time、首次 CI 通过率、返工、变更失败率、审查等待时间。
- [ ] 指定产品、技术、平台、策略、发布和服务所有者。
- [ ] 列出数据分级、禁止工具、保护路径、生产审批和不可逆操作。
- [ ] 选定每类工件唯一事实来源，并建立与工单系统的双向链接规则。

**退出条件**：试点范围和责任边界获得工程、产品、安全/合规共同确认。

## 1. 建立工件与反馈回路（第 3–4 周）

- [ ] 使用 `./bin/ain --target <业务仓库> init` 安装编排器，并运行 `./.ain/ain doctor`。
- [ ] 建立 `AGENTS.md`：架构、命令、代码约定、禁区、验证要求，控制在一页左右并纳入审查。
- [ ] 采用 `intent.md`、`spec.md`、`plan.md`、`verification.md` 模板。
- [ ] 将“计划接受后才能修改”和“验证通过后才能提审”写入 PR 模板/CI。
- [ ] 在实施前运行 `./.ain/ain gate <change-id> --through plan`，审查前运行 `--through verification`。
- [ ] 提供 Agent 可实际运行的 build/test/lint/视觉验证命令。
- [ ] 让团队以人工触发方式完成至少 10 个真实变更。

**退出条件**：80% 以上试点变更具有完整工件链和验证证据。

## 2. 策略即代码与确定性控制（第 5–7 周）

- [ ] 选择一条高频且常被遗漏的策略（例如外部 API 鉴权或 PII 日志）。
- [ ] 将其写为带命名所有者和版本的 Agent 策略/技能，并测试触发覆盖。
- [ ] 为不可妥协部分补充 Hook/CI：密钥扫描、保护路径、格式化、依赖策略或迁移检查。
- [ ] 设定最小权限：沙箱、网络许可清单、短期令牌和环境分层。
- [ ] 建立 `REVIEW.md`，启用机器审查 + 代码所有者分支保护。

**退出条件**：该策略在所有试点 PR 上可证明被应用，且违规被确定性控制拦截。

## 3. 评测与受控自动化（第 8–10 周）

- [ ] 从近期已接受的工作中沉淀 20–50 个 eval：任务、允许工具、验收检查、期望结果。
- [ ] 任何 `AGENTS.md`、策略、Hook、模型或工具配置变更都运行 eval。
- [ ] 为 Agent 写操作使用专用服务身份；所有写入经 PR，禁止直推主干。
- [ ] 先上线只读 CI 分诊（构建失败总结、测试波动识别、变更日志草拟）。
- [ ] 再允许开发/测试环境的低风险写操作。

**退出条件**：eval 阈值成为配置变更门禁；Agent 操作身份、输入输出和授权均可审计。

## 4. 闭环运维与规模化（第 11–13 周）

- [ ] 为一个服务定义控制带、阈值、触发动作、环境权限与升级人。
- [ ] 将告警接入“诊断 → intent/PR → 审查 → 发布”路径。
- [ ] 在预发布环境演练 Agent 触发的回滚，记录恢复时间与失败模式。
- [ ] 每次事故至少沉淀一项 eval、策略修订、Runbook 修订或意图工件。
- [ ] 复盘指标：交付速度提升不能以逃逸缺陷、越权或审查积压为代价。

**退出条件**：一个真实或演练事件可以从确定性触发进入受控流程，全链路可追溯且无人绕过生产闸门。

## 常见失败模式与纠偏

| 失败模式 | 早期信号 | 纠偏 |
| --- | --- | --- |
| 只增加代码生成，没有改流程 | PR 更大、审查更慢 | 强制计划和自验证工件；拆小变更 |
| 把策略放在长提示词里 | 同类违规反复出现 | 策略版本化；用 Hook/CI 强制关键规则 |
| 过早让 Agent 写生产 | 权限例外、人工紧急兜底 | 按 R0→R3 和 dev→stage→prod 分级授权 |
| 指标只看产出 | 代码量上升、事故也上升 | 同时绑定质量、安全、流动与学习指标 |
| Evals 一次性建设 | 模型/策略更新后效果漂移 | 把事故和漏检持续加入 eval 集 |
| 工件与 Jira 双事实来源 | 状态冲突、审计困难 | 声明唯一事实来源；另一端保存 ID + SHA 链接 |
